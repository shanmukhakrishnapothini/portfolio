Agentic AI Job Hunter

Finds entry-level AI and Python jobs, writes a tailored resume for each using only facts from my own work, scores it, and waits for my approval before applying.

What I do: I design and build the whole pipeline: the n8n job discovery, the FastAPI resume parser, the RAG layer on pgvector, the LangGraph workflow, the evaluation prompts and the MCP tools.

LLMs: Ollama models for job matching and resume tailoring. OpenAI, Gemini and Claude as ATS-score evaluators.

Python, FastAPI, LangChain, LangGraph, pgvector, MCP, n8n, PostgreSQL

Know more about this project

Why I’m building it

Looking for entry-level AI roles means reading many listings and rewriting a resume for each one, and it is easy to miss details or overstate experience. This platform does the discovery, matching and tailoring for me while keeping me in control of every application.

How it works

  1. Discover. n8n pulls openings from the Greenhouse and Lever public APIs and keeps those needing 0 to 1 years of experience for AI Developer, Agentic AI Developer, Generative AI Developer, Python Developer and Cloud AI Engineer roles.
  2. Parse. A FastAPI service reads my PDF and DOCX resumes, extracts skills and experience, and stores a structured candidate profile.
  3. Match. Ollama models, guided by prompt engineering, read each job description and compare its requirements with my profile.
  4. Ground. My projects and experience are embedded in PostgreSQL pgvector, and LangChain retrieves the most relevant pieces for each job.
  5. Tailor. The best base resume is chosen and rewritten for the job from the retrieved facts.
  6. Evaluate. OpenAI, Gemini and Claude each score the resume on technical skills, experience alignment and content quality.
  7. Revise. LangGraph routes the workflow with conditional logic: a weak score sends the resume back for revision, a strong one moves on.
  8. Track and approve. n8n, PostgreSQL and Python Excel automation record scores, dates and downloadable resumes. Nothing is sent until I approve it.

Design decisions

  • Resumes are built only from retrieved facts, so nothing is invented.
  • Separate models score each resume, so no single model decides alone.
  • MCP servers expose discovery, resume processing, evaluation and tracking as reusable tools.
  • A human approval step stays in front of every application.
Client project

Agentic IVR with MCP

A full agentic call experience where the AI takes the whole call and routes it to the appropriate agent when a person is needed.

What I do: I make changes to the system prompt, tools, services and the configurations shared in S3 and DynamoDB, and check the call logs in Splunk.

MCP, Genesys Cloud, Amazon Connect, Lex, Lambda, Polly, S3, DynamoDB, Splunk, CloudWatch, Cyara

Know more about this project

What makes it agentic

A traditional IVR walks the caller through fixed menus. Here an AI agent runs the conversation: it listens, decides what to do next, calls tools, and either resolves the request or hands the caller to the right person.

How it works

  1. The AI takes the call. The call reaches the contact center platform and is handed to an AI agent that listens and speaks in real time.
  2. It understands and acts. The agent works out what the caller wants and calls tools through MCP, such as REST services that validate the caller and look up account data.
  3. It routes to the right agent. When a person is needed, the agent decides which agent or queue is appropriate and routes the call there. Simple requests are finished by the AI itself.
  4. Configuration drives behavior. The system prompt, tool definitions, service settings and other configurations are shared through S3 and DynamoDB.
  5. Logs close the loop. Splunk and CloudWatch logs show what the agent heard, which tools it called and why it routed a call.

The foundation

This builds on my IVR work: Genesys Cloud call flows with menus, DTMF and speech input, queue selection and intent routing, plus Amazon Connect, Lex, Lambda and Polly integrations and REST lookups secured with IAM.

Project lead

Nova Lite and Nova Sonic AI Voice Assistant

A real-time voice assistant that answers company questions only from approved documents. I led it from requirements to a working POC for the client.

What I do: As project lead I gathered requirements, designed the solution, made the architecture decisions, coordinated team tasks and ran code reviews.

LLMs: Amazon Nova Lite for reasoning and responses. Amazon Nova Sonic for real-time voice. Both through Amazon Bedrock.

AWS, Bedrock, Connect, Lex, Lambda, DynamoDB, API Gateway, Polly, RAG

Know more about this project

The challenge

Callers need spoken answers they can trust, in real time, and only from approved company content. An assistant that guesses is a compliance risk, so grounding and response control were the core of the design.

How it works

  1. Call in. Amazon Connect answers the call and passes the caller’s speech to Amazon Lex, which captures the intent.
  2. Validate. Lex invokes a Lambda function that checks the input and calls Amazon Bedrock. When the answer needs live data, Lambda also reads DynamoDB and API Gateway services.
  3. Retrieve. Bedrock searches the Knowledge Base, built from approved documents in S3 with embeddings and semantic retrieval, and returns the relevant passages.
  4. Reason and answer. Nova Lite reasons over the question and the retrieved content under prompt and response-control rules. Nova Sonic carries the real-time voice conversation.
  5. Respond. A second Lambda formats the answer, Polly produces a natural voice reply, and Connect speaks it to the caller. CloudWatch tracks performance.

Keeping answers safe

  • RAG grounds every answer in approved content instead of the model’s own assumptions.
  • Prompt engineering, input validation and response-control rules reduce hallucinations.
  • Out-of-scope questions follow a defined response rule.

AI-Powered Microservices Application

FastAPI services that turn structured data into LLM summaries with adjustable length, tone and focus.

What I do: I built the FastAPI services, request validation, prompt templates and LLM integration, then tested them with Postman, containerized them with Docker and deployed them on AWS.

Python, FastAPI, Docker, AWS, Postman, Git

Know more about this project

The idea

Teams often need the same data summarized in different ways. This application lets other services request a summary and tune its length, tone and focus without any code changes.

How it works

  1. Intake. One service receives structured data and validates every request against a defined schema, returning clear structured errors.
  2. Prompt configuration. A second service builds the instructions from reusable templates that control length, tone and focus.
  3. Summarization. A third service calls the LLM with timeouts and retries, and exposes the summary as a reusable REST API.
  4. Operate. Logging and health-check endpoints support monitoring. The APIs are tested with Postman, documented, containerized with Docker and deployed on AWS.

Design choices

  • Separate services, so each part can be tested, extended or replaced on its own.
  • Timeouts and retries around LLM calls, so a failure degrades gracefully.
  • Configurable templates, so behavior changes without redeploying code.
